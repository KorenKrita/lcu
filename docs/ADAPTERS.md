# Harness adapters

LCU keeps the selected installed app's original CUA MCP server authoritative for instructions, execution, elicitation, policy, and lifecycle. It does not implement browser control, screenshots, accessibility, input, or JavaScript execution. The Pi client, Claude relay, and Codex relay use the official MCP SDK. The Codex relay passes original initialization instructions and public `js`/`js_reset` descriptors through, but intentionally omits `js_add_node_module_dir` and `turn_ended` from model-visible `tools/list`. It still forwards host calls to those original tools; the installed Codex Stop hook reaches `turn_ended` with the original session and turn IDs. This is an explicit visibility adaptation, not full `tools/list` parity.

## Shared client contract

```js
import { createCuaClient } from './adapters/client.mjs';

const cua = createCuaClient({
  command: ['/absolute/path/to/lcu'],
  onElicitation: async params => {
    // Render the original request. This placeholder cancels it.
    return { action: 'cancel' };
  },
});
await cua.connect();
const instructions = cua.instructions; // original MCP initialization instructions
const tools = cua.publicTools();       // original js and js_reset descriptors
const result = await cua.call('js', { code: 'await cua.getState()' }, { sessionId, turnId });
// Forward result.content and result.isError unchanged to the model.
await cua.turnEnded({ sessionId, turnId, event: 'Stop' });
await cua.close();
```

Before the first CUA call, the host must put the original initialization instructions and public tool descriptors into model context, as official Codex does. LCU registers no skill. Forward original result content and error state unchanged. Keep one connection alive through the turn and use real host session/turn IDs. `turn_ended`, `js_add_node_module_dir`, and Claude's `set_turn_context` are host-only tools; do not expose them to the model. Invoke original cleanup only for lifecycle events the host reports. The shared client cancels unresolved elicitation when `onElicitation` is absent. Otherwise, render the original request and return the user's actual response. `allowedOrigins` is only for exact HTTP(S) origins the user explicitly approved. LCU keeps no permission cache.

The shared client runs inside the harness process for Pi, Oh My Pi and Hermes, whose terminal UI is drawn on that process's stderr. It therefore pipes the original MCP process's stderr (which also carries the lines of LCU's macOS host and service) instead of inheriting it, reads it continuously so the process never blocks on a full pipe, and writes none of it to its own stderr. Each line becomes an `upstream_stderr` event in the [diagnostic log](#diagnostic-log), classified by its prefix and without its text. If the original process fails to start, the `connect()` error ends with its last stderr lines (at most 1000 characters), so the reason still reaches the harness. The Claude Code and Codex relays do not use this path: the harness starts them as stdio MCP servers and keeps their stderr in its own MCP log, so they leave the original process's stderr inherited.

## Linux sandbox state

The original `node_repl` reads `_meta["codex/sandbox-state-meta"]` (a `permissionProfile` and a `sandboxCwd` file URI) on every tool call. Without it, on a machine where bubblewrap works, it starts two Node processes through `$CODEX_CLI_PATH sandbox ... -- COMMAND` (bubblewrap, a read-only filesystem and a network-disabled seccomp filter): the JavaScript kernel, which runs the code the model writes in `js` calls, and the trusted worker, which hosts the Sky desktop service. The same seccomp filter also refuses `connect(2)` to the X11 Unix socket, so Sky cannot work inside it and every Linux computer-use call fails. Only a `disabled` profile removes the wrapper; the network field of a `managed` or `external` profile has no effect (observed with the Codex CLI the app ships: `network = {enabled = false}` in every sandboxed command line).

What each host sends: Codex CLI sends the metadata only to servers that advertise the `codex/sandbox-state-meta` capability, and the Codex relay does not advertise it, so it sends nothing; Claude Code, Pi, Oh My Pi, the Hermes bridge and generic MCP clients never send it.

**What LCU does (from 0.9.3).** The kernel stays sandboxed and only the Sky worker runs outside the sandbox. `lcu` sets `CODEX_CLI_PATH` to `bin/lcu-codex-sandbox` (implemented in `lcu/sandbox_shim.mjs`), which receives every command `node_repl` would give the real Codex CLI, and keeps the real path in its own configuration (`LCU_SANDBOX_SHIM`, which LCU adds to `NODE_REPL_UNTRUSTED_ENV_ALLOWLIST` because `node_repl` starts the kernel with only the listed variables). The shim is the only LCU code that decides what runs outside the sandbox, and it fails closed:

- `sandbox -- /bin/sh ...`, the availability probe `node_repl` runs first, goes to the real Codex unchanged. Refusing it would make `node_repl` conclude that no sandbox exists here and leave the kernel unsandboxed.
- A kernel command (`node --experimental-vm-modules <dir>/kernel.js --session-id ... --working-dir ...`, with the selected runtime's `bin/node`) goes to the real `codex sandbox` exactly as `node_repl` asked.
- A worker command (`<dir>/trusted-worker.js <path>`) runs directly, outside the sandbox, only when all of these hold: its parent process is the selected runtime's `bin/node_repl` (read from `/proc`); its Node resolves to the selected runtime's `bin/node`; its script is a regular file owned by the current user, not world-writable (group-writable only for the user's own group, for `umask 002`), inside a `.tmp*` folder of `$TMPDIR` that is owned by the user and holds `kernel.js` beside it; and `NODE_REPL_TRUSTED_SERVICES` names only `sky` and optionally `browser`, where `sky` is the selected runtime's `@oai/sky/service` or LCU's own input-translation wrapper and `browser` is `@oai/browser-desktop/service`, each present in the selected runtime. Any other worker is handed to the real `codex sandbox` as requested, with a note on stderr, so a lookalike service cannot escape the sandbox.
- Any other `sandbox` invocation (a different argument layout, profile shape or command) is refused with exit code 70 and a message on stderr. Nothing the shim cannot classify starts, and nothing starts unsandboxed. Other `codex` subcommands pass through unchanged.

Precedence is unchanged: per-call `_meta` overrides the default, and a `NODE_REPL_REQUEST_META` that already contains `codex/sandbox-state-meta` is left untouched. A host that sends a `disabled` profile therefore gets an unsandboxed kernel (the host's decision), and one that sends a restricted profile gets that sandbox with computer use still working, because the shim runs the Sky worker outside it in both cases. A host that registers bare `lcu` with Codex CLI directly would make Codex send its real turn profile, which now works; the relay registration sends nothing and gets LCU's default. If the shim file is missing from a release, LCU leaves `CODEX_CLI_PATH` alone and the original behavior (and its X11 failure) remains, which fails closed.

**What the kernel can and cannot do.** In the verified configuration the kernel cannot write the filesystem (`EROFS` on HOME, the workspace, `/tmp` and the approvals file), cannot connect to the network, to X11 or to D-Bus (`EPERM`), and `execFileSync` and similar synchronous spawns fail with `EPERM`. Asynchronous `child_process.spawn` is allowed by `node_repl` itself, but the child inherits the confinement (same filesystem, no network, seccomp mode 2). Computer use still works, because the model reaches the desktop only through the Sky worker's API. The kernel's JavaScript can still call that API, so it can control any application; the original Linux runtime has no per-app approval (only the macOS and Windows Sky targets ask for one), and the harness's own approval of LCU's tools remains the gate (see [Approval boundary](#approval-boundary)).

**Failure messages.** When the shim refuses a kernel command, `node_repl` reports "kernel exited unexpectedly" and includes the shim's message in the diagnostics the model sees. When it refuses a worker command, `node_repl` says only "trusted Node process exited unexpectedly; kernel reset, rerun your request"; its worker stderr is not forwarded, so the explanation (the shim's message and the `lcu update` hint) appears only on the MCP server's stderr in the harness's logs. LCU cannot add a model-visible message without proxying the original MCP server, which would be another implementation of it. `lcu doctor` prints one line saying whether the kernel is sandboxed on this machine.

**Where bubblewrap does not work.** In a container or on a host that restricts user namespaces, the availability probe fails and `node_repl` runs both processes directly, as before: the kernel is not sandboxed and `lcu doctor` says so.

**Modes.** `LCU_NODE_REPL_SANDBOX` must be in the environment of the `lcu` process. Unset is the default above. `host` leaves the original behavior untouched (no shim, no default; where bubblewrap works, the Sky worker is sandboxed too and cannot reach X11). `off` gives the original `node_repl` the `disabled` sandbox state official Codex sends under `danger-full-access` (the 0.8.2 to 0.9.2 default): neither process is sandboxed, the kernel runs with your account's permissions, and you should use it only on a machine where you accept that. Codex filters the MCP child's environment and LCU registers no `env_vars`, so `LCU_NODE_REPL_SANDBOX=off codex` never reaches LCU; set it under `[mcp_servers.lcu.env]` instead. The per-harness locations are in the [installation guide](INSTALLATION.md#linux-sandbox-and-input-notes), and `tests/codex_mcp_env.py` reproduces the filtering with an isolated Codex CLI. Pi, Oh My Pi and the Hermes bridge start `lcu` with their own process environment, so exporting the variable before launching them works.

`tests/adapter_paths.py` runs the GTK oracle flow through a bare client, the Codex relay, the Claude relay, the shared client used by Pi and Oh My Pi, and the Hermes bridge with no sandbox metadata; `tests/run.sh` runs it in a container where the sandbox is active and checks the negative control (`host`), the confined kernel with working computer use, a stricter host profile and `off`. `tests/node/sandbox_shim.test.mjs` covers the shim's recognition rules. The [verification record](verification/linux-kernel-sandbox-2026-10-05.md) lists the live checks.

## Linux window-targeted input

The original Linux engine (`sky_linux`) delivers input that names a `window` (`app.pressKey`, coordinate `app.click`, `scroll`, `drag`, pointer moves) with `XSendEvent`, without activating the window. GTK 4 reads only XInput2 and ignores all of it; Qt ignores the scroll wheel events. Desktop-level calls (no `window`, XTEST) reach every toolkit. LCU interposes on the Sky RPC seam, as the Windows trusted-service wrapper does, and for these cases only issues the same action through the engine's own desktop-level call:

1. The target window's process is identified, and only when the X server itself vouches for it. LCU reads `_NET_WM_PID` and `WM_CLIENT_MACHINE` (through `xprop`, which LCU's required `x11-utils` package provides). `_NET_WM_PID` is the client's own claim, in the client's PID namespace (EWMH), so a client sharing the X socket from another PID namespace (a Flatpak application, a container) can advertise an id that collides with an unrelated local process. LCU therefore also asks the X server for its own record of the window's client: the X-Resource extension (`XResQueryClientIds` with `XRES_CLIENT_ID_PID_MASK`, X-Resource 1.2) returns the process id the server observed on the connection (`SO_PEERCRED`) and nothing for a client on another machine. LCU asks it over the display socket itself (`lcu/x11.mjs`: the few X11 core, X-Resource and XTEST requests named here, no client library and no other process), only for a window that would otherwise be translated (the toolkit and method are decided first, so an untranslated request, such as a Qt key, a Chromium window or a hidden window, never asks the X server; a translated one costs one short connection for the identity and one more for the pointer check below). SO_PEERCRED process ids are relative to the PID namespace of the X *server*, so a server outside LCU's namespace (LCU in a container or child namespace, X outside) would report ids that mean nothing here. Equal numbers in two PID namespaces prove nothing (a process that is pid 4000 in a child namespace and 4000 in the server's can be made to match), so the proof comes from the actual socket. LCU resolves the display's local socket (`:N` or `unix:N`: the abstract `@/tmp/.X11-unix/XN` and the file `/tmp/.X11-unix/XN`; a TCP, remote or malformed display fails closed), finds the listening socket inodes in `/proc/net/unix`, finds every process holding them through `/proc/*/fd` (only processes LCU may read), and requires each holder's `/proc/<pid>/ns/pid` link to equal its own. A process listed in LCU's `/proc` is in LCU's PID namespace or one below it, so a server in a parent or sibling namespace is never found, and a server whose descriptors cannot be read (another account, a non-dumpable setuid process) or that cannot be identified fails closed. Before trusting any id the same connection additionally asks the server for LCU's own client (a 1x1 window it creates and never maps) and requires the reported id to equal LCU's `getpid()`; a mismatch means no id. Both conditions must hold. The proof runs for every question rather than being cached, because each question opens its own connection and the extra query is one round trip on it, so there is no stale answer after an X server restart. A window is eligible only if `WM_CLIENT_MACHINE` equals the local host name, the X server's process id equals `_NET_WM_PID`, `/proc/<pid>/ns/pid` and `/proc/self/ns/pid` are both readable and equal (an unreadable link of either kind means "not shared"), and `/proc/<pid>/maps` shows `libgtk-4.so` (GTK 4) or `libQt5Core`/`libQt6Core` (Qt). A process that also maps `icudtl.dat`, `libxul.so` or `libffmpeg.so` (Chromium, Electron, Firefox) is never classified as GTK 4. The toolkit is cached for ten seconds per (PID, process start time from `/proc/<pid>/stat`, field 22) and revalidated on every use; the X-Resource id is asked again for every translated request. **Fail closed:** no id from the server (remote client, X-Resource extension missing, query failure), an id that differs from `_NET_WM_PID`, another PID namespace or an unreadable `/proc` all mean the request goes to the original service untouched.
2. For a GTK 4 target, `press_key` (atomic chords), `click` (including double), `scroll`, `drag` and `move` are translated; for Qt, `scroll` only. `key_down` and `key_up` are **not** translated and are always passed to the original service unchanged, so a held key on a GTK 4 window behaves as in the original engine: the `XSendEvent` hold is ignored. To hold a key for a GTK 4 window, activate it and use the desktop-level `key_down`/`key_up` (no `window`), which the engine delivers with XTEST; release it with the matching desktop-level `key_up`. LCU keeps no key state. `typeText`, `paste`, AT-SPI element actions (`element_id`), screenshots, state and every other app go to the original service unchanged.
3. Serialization. Every call that can change focus or input state goes through one queue, translated or not: `activate_window`, desktop-level and window-targeted input of any kind (including `key_down`/`key_up`, `typeText` and untranslated fallbacks), and unknown methods. Read-only calls (`list_windows`, `list_apps`, `get_screenshot`, `get_window_state`) bypass it. A translated request reads the window list, the modal state and the focus only after every earlier queued call has finished, so nothing interleaves between its final focus check and its input (an `activate_window` of another window cannot slip in; a pass-through call cannot either). Every call the queue makes to the original service is bounded (30 s; `LCU_LINUX_INPUT_CALL_TIMEOUT_MS` overrides it, for tests). A translated call whose duration follows from its input gets more: a drag adds 20 ms per path point and 2 ms per pixel of path length (the original engine took 4 to 10 ms per point on the hosts measured, so a valid 4,000-point drag can need about 40 s and is not killed at 30 s), a click adds its hold `duration` for each click, a key chord adds its hold `duration`; the total never exceeds 5 minutes (or the base bound, if that is larger). The caller's own JavaScript timeout is separate and still applies: the original Sky service and its Linux transport have no request timeout of their own, so one hung engine call would otherwise hold every later input and focus call forever. Racing a timeout would be unsafe, because the abandoned call could still deliver its input in the middle of a later request. On a timeout, if the call is a translated one that may already have pressed something, LCU first ends the engine, then releases what that call itself pressed (see "Input state" below), and then stops the trusted worker process, after ending the original `sky_linux` engine process itself (SIGTERM, then SIGCONT, because a stopped process acts on a pending signal only once continued; ChatGPT 26.915.31945's transport kills its child when the worker exits, 26.928.31416's leaves it running with no parent, and an engine that resumed later would still deliver the call's input), rejects the call with an error, and refuses every call queued behind it with a "restarting" error without sending it. `node_repl` reports the worker's exit and starts a fresh worker, with a fresh engine, for the next request; the original `node_repl` offers no other way to replace a trusted worker or to cancel one call, and the original JavaScript timeout (30 s by default) only ends the JavaScript call, not the call still running in the worker. If the target is not listed or is minimized, the original request is sent and the engine reports its normal result. If the target owns a modal dialog (a transient window listed with `modal: true`), keyboard input goes to the dialog, because the toolkit's grab discards input for its parent; pointer input to such a parent is refused with an error naming the dialog, because the parent's coordinates do not describe the dialog (target the dialog window explicitly, with coordinates relative to it).
4. A pointer action's point (the point of a click, scroll or move, the start of a drag) must lie inside the target's current client rectangle, `0 <= x < width` and `0 <= y < height` using geometry read immediately before the call (and again after any activation); otherwise the call fails with an error and nothing is sent, instead of clicking whatever application is at that spot of the desktop. A drag may end outside the target. Bounds are not enough, because XTEST follows normal pointer routing: a notification, tooltip or override-redirect popup can lie over a target that is already focused (activation is then skipped, so nothing raises the target above it), and the click would land on the overlay. Immediately before a translated desktop-level pointer action (click, double click, scroll, a drag's start point, move) LCU asks the X server for the chain of mapped windows at the converted desktop point (`TranslateCoordinates` from the root down; read-only, nothing moves, input shapes are honored, so click-through windows are transparent) and the target must be in that chain, meaning the deepest window there is the target or one of its descendants (a window-manager frame above it is fine). Any other window, or no answer, fails the call with an error and sends nothing. The same connection first asks whether another client holds an active pointer grab (a popup menu, a drag in progress), because the click would go to the grabbing client whatever window is at the point: it tries `GrabPointer` on the root window with no event mask and undoes it with `UngrabPointer` at once; `AlreadyGrabbed` or `GrabFrozen` refuses the action, and any other result (or no answer) refuses it as undeterminable. The probe changes nothing on the desktop, but for the round trip of that request (well under a millisecond) pointer events are not delivered to anyone, and the toolkit may see a crossing event with grab mode; a physical click in that instant could be lost. It runs only for pointer actions that would otherwise be sent. The check runs inside the queue directly before the call; the remaining gap is the time between the server's answer and the engine's click.

Input state. On the same connection LCU reads which pointer buttons and keys the X server reports pressed (`QueryPointer`, `QueryKeymap`). If a translated call times out, or fails by itself, after it may have pressed something, LCU reads the state again and releases through XTEST (`FakeInput` button and key releases) only what is pressed now, was not pressed before the call, and is of a kind the call could press: the button its action uses (a click's `mouse_button`, Button1 for a drag, the wheel buttons for a scroll, none for a move), and the keys of a held chord (a key press, or a pointer action's `key`). Buttons and keys that were already down are left alone. It runs before the worker stops, so a later pointer motion cannot continue a drag; the engine is ended first, so it cannot press again; a call that never reached the engine releases nothing.

Known limits: the gap between the checks and the engine's XTEST delivery cannot be closed from outside the engine (a popup mapped, or a grab taken, in that interval is not seen); only active pointer grabs are detected (passive grabs, such as a window-manager Alt-click binding, and keyboard grabs are not, so a translated key can still be taken by a client holding a keyboard grab); only the pointer, one X screen and the windows a window manager reports were tested, with Openbox and Xfwm4 (other window managers and compositors, XInput2 grabs by toolkits that bypass the core protocol and Wayland are not covered); the release after a timeout cannot restore anything that was pressed before the call or was pressed by something else. A converted point that is off screen keeps the original service's behavior and error.
5. Unless the window is already focused, LCU calls the engine's `activate_window` and waits for the engine to report it focused; if it does not, or if the focus has moved away again when the geometry is read right before sending, the call fails with an explicit error rather than sending keys to some other window.
6. Window-relative coordinates become desktop coordinates, `window.x + x` and `window.y + y` (device pixels, the engine's own unit), and the engine's desktop-level `press_key`, `click`, `scroll`, `drag` or `move` runs with the other fields unchanged, so the engine owns the whole chord, including pressing and releasing its modifiers. The caller gets that call's result, the same shape as before.

Consequences, visible to the user: the target window is focused (and raised by the window manager when it was not) and the real pointer moves; a window that is already focused is not raised, which is why an overlay above it is checked for and refused rather than assumed away. GTK 3, Firefox, Chromium, Electron and terminals keep working in the background without either. Input and focus calls run one at a time, each bounded by the timeout above.

`LCU_LINUX_INPUT_TRANSLATION=off` (also `0`, `false`, `no`) disables the wrapper; set it in the environment of the `lcu` process as described in the [installation guide](INSTALLATION.md#linux-sandbox-and-input-notes). A tested app/runtime pair in [tested-versions.json](../tested-versions.json) may list `"native_input": ["gtk4", "qt-scroll"]` once the pair itself was verified to handle that toolkit natively; LCU then skips the translation for exactly that pair, and any other version stays translated. See [the adaptation record](STANDALONE-ADAPTATIONS.md) for the evidence and removal criterion.

## Pi extension

The Pi adapter uses Pi's extension API and the shared MCP client. In `before_agent_start`, when Pi provides `event.systemPromptOptions` (checked in Pi 0.86.0), the adapter appends the original initialization instructions once to `systemPromptOptions.appendSystemPrompt` and returns no `systemPrompt`; returning one makes Pi force-replace its structured prompt and stops tool additions from being tracked as deltas, so each `tool_search` discovery would change the request prefix and miss the prompt cache on OpenAI/Codex models. Without `systemPromptOptions` (older Pi, OMP) the adapter returns the appended prompt as before (see [Oh My Pi](#oh-my-pi)). This path is backed by unit tests and Pi source reading, not live Pi verification. It keeps the connection through model rounds and sends cleanup after the full prompt. If cleanup fails or the original host reports its turn-ended timeout (`LCU_TURN_CLEANUP_TIMEOUT` from the shared client), Pi warns instead of failing the turn, retries the cleanup at the next `agent_start`, and refuses LCU tool calls until it succeeds. Its UI presents original native-app persistence choices and browser-origin requests; headless mode cancels. Current package registration and result forwarding passed with Pi 0.87.1 from `@earendil-works/pi-coding-agent`; see [the standalone host record](verification/latest-standalone-harness-2026-09-27.md). Earlier desktop-task evidence below used Pi 0.73.0.

The adapter starts the original runtime only when a session needs it. Pi needs the tool definitions and the initialization instructions before its first model call. After a connect, the adapter keeps that surface in a module-scope map, so a subagent child that shares the evaluation shares it, and in `pi-surfaces.json` in LCU's cache directory (`lcu/check_record.mjs`: `~/Library/Caches/lcu` on macOS, `${XDG_CACHE_HOME:-~/.cache}/lcu` on Linux). The file is the same kind of record as the other launch caches: `readRecord` and `writeRecord`, mode `0600`, replaced atomically, at most 8 entries. Creating the cache directory does not change the mode of one that already exists. An entry must hold exactly `js` and `js_reset`, each with a description and an object input schema, and the instructions; anything else is a miss. The key is a SHA-256 hash of the launch command, including flags such as `--chrome`, the files it names, `LCU_APPROVED_ORIGINS`, the environment the original launcher reads for its instructions (`CUA_REPL_ENABLED_SURFACES` and the other instruction variables), the platform and architecture, the per-account cache directory, whether the adapter is Pi or Oh My Pi, the release directory and its `bundle.json`, and the app and CUA runtime versions. A command name without a slash is looked up on the `PATH` that the runtime process receives from the MCP SDK's stdio transport, as Node looks it up to start that process. The versions come from the app's files without starting the app or the runtime: on macOS `Info.plist` and `cua_node/manifest.json`; on Linux `cua_node/manifest.json` and the `app.asar` size and modification time. If the command does not run an LCU release whose versions can be read, the adapter neither reads nor writes the cache. When the surface is known, `before_agent_start` registers the tools and appends the instructions without a connect, and the runtime starts on the first LCU tool call or `/lcu pick`. Otherwise `before_agent_start` connects as before. Oh My Pi needs the tools registered while the extension loads. A known surface does that without a connect; an unknown one still connects then, and a later Oh My Pi session reuses that entry. If a connect reports a different surface, the adapter serves the call, registers the new tools, replaces the entry, and logs one `surface_changed` event; changed instructions take effect at the next `before_agent_start`. `agent_end` and `/lcu stop` do not start a runtime that the session has not started. The cache is off on Windows, whose `lcu.cmd` launcher selects a release through `current.json`. `LCU_SURFACE_CACHE=0` turns it off. `adapters/test/pi-surface-cache.test.mjs` covers these paths.

Pi also registers `/lcu stop` and `/lcu pick`:

```text
/lcu stop
/lcu pick
```

`/lcu stop` requires an interactive Pi session on macOS and an active LCU turn. It lists the original Computer Use apps observed for that turn, asks which app to stop, and sends the exact session, turn, and app identities to the private host-control channel. The host validates the active turn and invokes the installed original Stop method. A task-owned macOS guest verified that the next same-turn action returned the original stopped-for-this-turn error and that the original turn-ended hook recovered a distinct next turn with an exact 39-byte save oracle. LCU sends the original `ComputerUseIPCCodexTurnEndedRequest` with the captured session, turn, and metadata, then retains the existing CLI cleanup notification. Two guest runs accepted Stop while a `type_text` MCP call was pending; that call returned the original stopped-for-this-turn error and a fresh turn completed the 39-byte file oracle. This proves the MCP result and recovery behavior, not interruption of native input at a particular keystroke boundary. The Pi slash-command UI has not been exercised end to end. See the [current Stop verification](verification/headless-stop-implementation-2026-09-27.md).

`/lcu pick` requires Pi's interactive selection and editor APIs and runs only while no LCU turn is active. It selects an original app, browser/profile, and session or open user tab, then appends target guidance to the current editor draft. It does not submit the draft or claim an open user tab. The command is unavailable in headless Pi mode; browser and app availability depends on the original provider. Picker guidance asks the next request to revalidate the selected target, but cannot enforce later model behavior. Installed Pi 0.87.1 source executes registered slash commands inline before its normal streaming queue and its interactive UI can present the selector while the agent is active. Native-app selection passed a live Linux Pi UI smoke test. A separate live browser-tab TUI test on the final 0.4.2 runtime selected an open Chrome extension-provider tab by exact profile and tab identity and inserted guidance into the actual editor draft; it did not submit the draft, claim the tab, or contact a model provider. The `/lcu stop` menu has not been exercised end to end. See [the request-context and picker verification](verification/request-context-2026-09-27.md) for evidence and behavior limits.

`LCU_APPROVED_ORIGINS` is read only by the Pi and Oh My Pi extension. It holds a JSON array of exact origins the user already authorized; for those origins the extension accepts the runtime's site prompt without asking, and any other origin goes to the user through Pi's UI (print and headless modes cancel). It only answers a prompt the runtime actually sends, so it cannot lift a saved denial; see [Chrome site decisions](INSTALLATION.md#chrome-site-decisions).

A model-driven Linux GTK task and an opt-in official Chrome-extension task are recorded in [Pi verification](verification/pi-generated-gtk-real-model-2026-09-24.md). The [approval scope test](verification/native-app-approval-scopes-2026-09-25.md) verifies response forwarding, not grant persistence across helper restart or revocation. The [dismissal regression](verification/pi-approval-2026-09-26.md) verifies that dismissing an origin prompt cancels it and that an unrelated request is not accepted through an origin allowlist.

## Hermes Agent

Register the experimental Hermes integration with `lcu setup --agent hermes`. Setup stages the native Python plugin under the selected profile's `plugins/lcu-cua`, and invokes `hermes plugins enable lcu-cua`. It preserves unrelated Hermes configuration through Hermes's own enable command. Set an absolute `HERMES_HOME` for a named or custom profile. Hermes plugins have profile scope, so `--scope project` is rejected.

The plugin uses a private Node bridge backed by the shared official MCP SDK client. Host lifecycle and request metadata remain outside the model-visible tools. Original native-app approval requests use Hermes's native selector with once, session, and always choices restricted to the scopes the original runtime offers. LCU forwards the selected scope to that runtime and keeps no grant cache. Original browser-origin requests offer once or deny. Where no one can answer, namely `hermes -z`, `hermes chat -q`, cron, or any run without a registered approval callback, approval requests cancel immediately instead of waiting on stdin. Unsupported forms and URL approval flows cancel. Images use Hermes's native multimodal result envelope; audio is saved byte-for-byte and represented by a local file reference, as in Pi. The original installed app still supplies execution, schemas, instructions, and permission requests.

The model gets the original `js` and `js_reset` descriptors as the registered Hermes tool schemas. The original initialization instructions, under one line naming LCU, are registered once with `ctx.register_system_prompt_section("0-lcu-cua.instructions", ...)`: Hermes renders the section into each new session's system prompt and keeps those bytes for the session. Hermes skips, with only a log warning, a section over 4,000 characters (or over its 8,000-character total for all plugins), so LCU does not register instructions longer than 4,000 characters; it adds them to the first user message of each session instead (`is_first_turn`), as it does on a Hermes without the section API. Nothing is cut. Hermes adds sections sorted by ID until that total is used, so the section ID starts with `0` to come before any ID starting with a letter; the section is about 180 characters with the instructions observed on 2026-10-21, so it always fits when first. Only another plugin with an ID sorting earlier can still push it over the total, and Hermes's hook gives LCU no way to detect that skip. The `pre_llm_call` hook still runs every turn for turn lifecycle and session ownership, and returns text only for that fallback or when LCU is unavailable for the turn (missing session or turn ids, failed cleanup of a prior turn, another session owning the runtime, or a failed reconnect). Hermes appends hook text to the user message and replays it on later turns, so successful turns add none. Switching to another session reconnects the original runtime and refuses the turn if its tool descriptors or instructions changed, because the session prompt already holds the previous ones. Hermes v2026.9.24 (0.21.5), the verified release, already has the section API.

Nothing from LCU is written to the Hermes terminal. The plugin starts the bridge with its stderr piped and drained by a background thread; up to 200 lines per bridge (the original runtime's own stderr is already in the diagnostic log, so these are the bridge's rare messages) go to the plugin's Python logger at `INFO`, and so to whatever handlers Hermes has configured (for example its log files); without a handler they are dropped. Which Hermes versions configure such handlers was not checked. A failed turn cleanup is logged as a warning on the same logger, only when a handler is configured, and stays pending: the next turn retries it and, if it still fails, tells the model that LCU is unavailable.

Hermes v2026.9.24 (0.21.5) passed a real model-directed Linux ARM64 GTK save flow with an independent file oracle. Its public execution middleware supplies exact turn and call identities omitted by ordinary plugin-handler dispatch. See [Hermes verification](verification/hermes-harness-2026-09-28.md) for source evidence, session isolation, and remaining browser, approval, and platform limits.

## DeepSeek Harness

Register the experimental DeepSeek Harness (DSH) integration with `lcu setup --agent dsh`. DSH's MCP client advertises no elicitation support, so a plain MCP registration would fail every macOS app approval and never end LCU's turns. LCU therefore ships a native DSH host plugin, `adapters/dsh/plugin.mjs`, and setup installs it with DSH's own `dsh plugin --profile PROFILE add DIR`. The profile is `desktop` (the app's) by default; `--dsh-profile NAME` selects another, such as `web`. DSH changes the desktop profile only while DeepSeek Harness Desktop is closed, so setup refuses that profile while the app runs. Setup uses `dsh` on PATH, else the CLI inside the installed app (`DeepSeek Harness.app/Contents/Resources/runtime/cli/bin/dsh`). An absolute `DSH_HOME` selects another DSH home. DSH profiles have their own plugins, so `--scope project` is rejected.

Setup writes a small bundle per profile under `~/.local/share/lcu/dsh/<profile>-<hash>/` (`package.json` with `engines.dsh` `>=0.2.1-rc.2 <0.3` and `dsh.bundle.patch`, `cordis.patch.yml` inserting the `lcu-computer-use` row with the runtime command as its config, `index.js`, a locale file and an original icon). DSH links that directory into the profile (`link:`), it does not copy it. `index.js` imports `createMcpToolDefinition` from DSH's `@deepseek-ai/dsh-mcp-client` and passes it to LCU's plugin, imported by relative path from the release. DSH resolves its own packages only for files of a linked bundle that lists them as `peerDependencies`; the same import from LCU's release files fails, so the bundle declares that peer and the plugin takes the helper as an argument. The bundle's `apply` is an `async function`: Cordis 4 constructs a plugin function that has a prototype instead of awaiting it, and a headless run then sent its first model request before LCU's tools existed. Remove the plugin with `dsh plugin --profile desktop remove lcu-computer-use` (with Desktop closed), then delete its directory under `~/.local/share/lcu/dsh/`.

The plugin connects the shared client when DSH loads it, registers exactly `js` and `js_reset` (DSH's helper gives their results DSH's own content and image handling) and adds the original initialization instructions as the prompt section `lcu-computer-use` (order 3100, beside DSH's MCP servers section, not interpolated). Each call carries the DSH session id, the call id, the agent's model and reasoning effort, and an LCU turn id created on the first call of each DSH turn, read from DSH's `turnBoundary` projection. DSH's `turn/end` session event ends that turn upstream with `Stop` for a completed turn and `Interrupt` for every other reason (aborted, error, blocked, max tokens). A failed end stays pending: the session's next call retries it first and, while it still fails, refuses with "LCU is still finishing the previous turn". A disposed session or an unloaded plugin interrupts its open turns, then the plugin closes the client. A disposed session whose end fails is kept until a later call of another session or the plugin's unload retries it successfully. The `lcu` process gets DSH's environment without its `DSH_*` variables and without names that match `KEY`, `PASSWORD`, `SECRET` or `TOKEN` (DSH passes provider keys through its environment); LCU reads none of them. Audio results are saved to files as in Pi.

Native-app approvals use DSH's question card (`userQuestions.ask`, the seam DSH's own computer-use code uses for app consent) with the choices the original runtime offers: Allow once, Allow for this session when offered, Always allow when offered, and Decline. The card is shown in the agent of the call in progress; with calls of two agents in flight, or without the question service, the request is cancelled. A cancelled, aborted or delegated question (`ASK_CANCELLED`, `ASK_ABORTED`, `DELEGATED_CALLER`), a typed answer, and a run without an answerer (`NO_PROVIDER`) all cancel. Only the web UI answers questions, which DSH Desktop uses; `dsh --profile headless` and ACP clients have none, so approvals there fail closed, as in other hosts without a selector. Other empty forms offer Allow or Decline; forms with fields and URL requests cancel.

Images reach the model only when DSH's selected model declares image input. OpenRouter's DeepSeek models and `deepseek-v4-pro` are text-only, so a screenshot becomes DSH's `[image unavailable]` placeholder and the model works from LCU's text accessibility state; DSH's direct `deepseek-flash` route takes images. `DSH_TOOLS_MODE=ptc` hides native tools from the model, so `js` is reachable only through DSH's code mode. DSH's experimental Auto review permission preset reviews tool calls before they run, which can include LCU's.

Unit tests (`adapters/test/dsh.test.mjs`, `tests/node/harness_setup.test.mjs`) cover the tools, prompt, call metadata, every approval choice and failure, turn ends with retry, the environment, the generated bundle and the Desktop check. A scratch-profile check against DSH 0.2.1-rc.2 on macOS arm64 confirmed the linked install, the peer resolution, and that a headless run's first request carries `js`, `js_reset` and the instructions. A live Desktop run with DeepSeek V4 Flash and Pro on macOS arm64 ([record](verification/dsh-macos-2026-10-21.md)) confirmed tool calls, the approval card with a session grant, and `Stop`/`Interrupt` turn ends. Headless fail-closed approval is covered only by unit tests; image input, Windows, Linux and macOS x64 are unverified.

## Junie

Register the experimental Junie (JetBrains) integration with `lcu setup --agent junie`. Junie's MCP client advertises no elicitation support, sends no request metadata and ignores a server's initialization instructions, so a plain MCP registration could never ask for an app approval, never end LCU's turns, and would hide the original instructions from the model. LCU therefore registers a relay, `adapters/junie.mjs`, as Junie's `lcu` MCP server and adds Junie hooks that run the same file with `--hook`. Setup needs no `junie` executable: it writes two of Junie's user files and runs nothing.

- `~/.junie/mcp/mcp.json`: `mcpServers.lcu` with the release's Node, the relay and the `lcu` command, and `timeout` 3,600,000 ms (Junie's maximum; its 60 s default would end long `js` calls).
- `~/.junie/config.json`: one LCU command hook each for `SessionStart`, `UserPromptSubmit`, `Stop`, `StopFailure` and `SessionEnd`. Earlier LCU hook entries are replaced and every other hook is kept. Junie reads hooks only from this user file (a project `config.json` is ignored by default), so `--scope project` is rejected.

The relay lists exactly the original `js` and `js_reset`, and owns the turn ids. Junie starts MCP servers and hooks as direct children of its own process, so the relay listens on a private Unix socket named after that parent and its own pid (`$XDG_STATE_HOME/lcu/junie`, default `~/.local/state/lcu/junie`, or `$TMPDIR/lcu-junie-<uid>` when that path would not fit a socket name; mode 0700, owner checked). A hook finds the socket of its Junie process and passes the event and Junie's `session_id`. `UserPromptSubmit` ends the session's previous open turn (`Stop`, or `Interrupt` while a call is still running) and, on the first prompt of each session, returns the original instructions, under one line naming LCU, as `additionalContext`, which Junie prepends to the prompt. A `js` call opens a turn for the current session. `Stop` (a completed task) ends it with `Stop`; `StopFailure` (an API error) and `SessionEnd` with `Interrupt`. A session that starts while another has an open turn interrupts that turn. A failed end stays pending and is retried before the next call of any session, which is refused with "LCU is still finishing the previous turn" while it still fails. When Junie closes the relay, open turns are interrupted (at most 2 s). Hooks never print anything except that context and never fail a Junie step; with no relay they do nothing.

**With Junie, app approvals are permanent until revoked**, until JetBrains ships elicitation support in Junie's MCP client. Native-app approvals cannot be asked in Junie. The relay cancels each request (the host guard still declines agent host apps first), and, when it is the only call in flight (an approval request does not name its call), the call's result gets one more text block telling the model to run `lcu apps allow <App>` itself in a terminal (the person approves with Touch ID or the account password) and retry; if the command fails, is refused or times out, to ask the person to run it and stop; and, when its task is done, to tell the person which apps it allowed and offer to run `lcu apps revoke <App>`. The command is the absolute `lcu` launcher setup passed to the relay. Apps allowed that way stay allowed for every agent until `lcu apps revoke <App>`. `lcu setup --agent junie` prints this as a warning and, when interactive without `--yes`, asks `Continue? [y/N]` before registering Junie; answering no skips Junie. Nothing about it is added to the session-start context. Browser-origin requests are allowed only for the exact origins in `LCU_APPROVED_ORIGINS` in the relay's environment, as in the shared client, and cancel otherwise.

Junie CLI 26.10.20 on macOS starts the MCP server only after a session's first `SessionStart` and `UserPromptSubmit` hooks, so the relay is not yet listening for them: that prompt's calls run under the relay's own session id, the first ending hook (`Stop`, `StopFailure` or `SessionEnd`) ends that turn and names the session, and the original instructions do not reach the model on that first prompt (a single headless `junie --task` run never receives them; an interactive session gets them with its next prompt). Junie decides per prompt, with a model call, which MCP tools to offer, so a prompt that does not suggest computer use may not see `js`; the tools appear to the model as `mcp_lcu_js` and `mcp_lcu_js_reset`. The interactive TUI asks before each MCP call unless [`--approval auto`](INSTALLATION.md#approval-mode) is used. Subagents share their parent session's turn. Audio results are saved to files as in Pi. Instructions are added once per session per relay process, so a resumed session gets them again.

Unit tests (`adapters/test/junie.test.mjs`, `tests/node/harness_setup.test.mjs`, `tests/node/approval.test.mjs`, `tests/node/setup.test.mjs`) cover the tools, the instructions, every hook event, turn ends with retry, session switches, the approval hint, the setup warning and confirmation, the host guard, silent hooks, stale sockets, the setup files and the allowlist entries. Junie CLI 3110.7 on Linux x64, with a scripted model provider and the MCP fixture as the runtime and the files setup wrote, confirmed headless and interactive runs: `js` calls carried Junie's session id, each prompt's turn ended on `Stop`, the instructions reached the model's prompt, the approval hint reached the model, and with `--approval auto` the TUI did not ask. Desktop control on macOS, the JetBrains IDE plugin (whose hooks are unverified; without hooks a turn ends only when Junie exits), Windows (setup refuses it) and a live model are unverified.

### Native-app approvals in Claude Code and the Claude app

On macOS and Windows the original runtime asks per app (`Allow Computer Use to use "Zed"?`) with an MCP form elicitation. The relay forwards it to Claude Code as a form with the choices Allow once, Allow for this session, Always allow (only when the runtime's `_meta.persist` offers it) and Decline.

- **Terminal, without the mod:** Claude Code draws that form and the relay maps the answer. This is unchanged.
- **Claude app Code tab and the VS Code extension, without the mod:** the host has no elicitation callback and declines at once, so the runtime reports "Computer Use was not approved". This is a host limitation, tracked upstream in anthropics/claude-code #96043 and #89858.
- **With the `lcu-approve` mod** (installed by `lcu setup --agent claude-code`, see [below](#the-lcu-approve-mod)): the terminal and the app show one native approval with the choices of the Codex card: Allow this conversation (the runtime's `session` scope), Always allow (`always`, only when offered) and Deny. The terminal shows it as a pane; the Claude app's Code tab as the engine's own question card, so the app flags the session as needing input (see [below](#the-lcu-approve-mod)). The pane shows the app's name and bundle id (and its icon: converted once from the app's `.icns` with `sips`, or drawn by the system for asset-catalog icons, and kept in the mod's store; nothing is shown when no icon can be made), then "Computer use will be able to see and control <app>." A runtime `riskLevel` of `high` adds a "High risk" badge and the runtime's own warning text (`warningSubtitle`, or `subtitle`). Allow this conversation is the primary button (hotkey `a`), Always allow the secondary one (`l`), Deny the dismiss-style one (`d`); letters, because digits need Shift on an AZERTY keyboard. A press records the choice, shows a toast ("Calculator allowed for this conversation"), and closes the pane. On the app the icon is an `Svg` tile (the picture embedded over the app's initial); on the terminal it is an `Image` where the terminal draws images (kitty graphics), else blank space. Anything else the runtime asks (Chrome sites, for example) is left to the host.

#### The `lcu-approve` mod

A mod can hook the elicitation (`classic.Elicitation`) but cannot answer it: Claude Code lets it only `block` the event, after which the host answers `decline`. So the person's choice reaches the runtime through LCU:

1. The relay receives the runtime's elicitation, keeps a pending record (id, bundle id, label, offered scopes, risk, warning, message) and forwards the form to the host exactly as before.
2. The mod's hook fires first. It calls the relay's host-only tool `approval_request` with the elicitation message, which receives the record and marks it as claimed (the mod will answer), opens a pane titled "Computer use approval" with the question, the app and its bundle id, the warning, and Buttons for the choices, and returns `{ block }` at once. No hook stays pending while the person decides: the Claude app delivers a pane's presses to the mod only when no hook of the mod is in flight, so a hook that waited for the press deadlocked (the app log read `ui_press not handled`).
3. The host's own form is blocked, so the host answers `decline` (or `cancel`) immediately. Because the record is claimed, the relay does not pass that answer on: it keeps the runtime's elicitation open and counts the wait as a pending approval, so tool-call deadlines stand still. A button press calls `approval_choice({id, choice})`; closing the pane records `cancel`. The mod then takes the pane down.
4. The relay answers the runtime from the recorded choice: `session` or `always` become `accept` with `_meta.persist`, Deny becomes `decline`, a dismissal `cancel`. The record is deleted afterwards. If the request ends first (the runtime cancels the elicitation, or the call is interrupted with no other call alive) the wait ends, the runtime gets `cancel` and a later `approval_choice` is refused as an unknown id, which is how the mod learns its pane is stale. A record the mod never claimed (no mod, or an elicitation it does not handle) is answered from the host's answer as before, and an `accept` from the host is also used as is.

In the Claude app (a session whose `$.session.surfaces()` includes `desktop`, even with a terminal attached too, or one with no surface attached that Claude Code runs with `CLAUDE_CODE_ENTRYPOINT=claude-desktop`: with engine 2.1.304 the app had attached no surface when an approval arrived, and the mod's headless check then left the form to the app, which declined it) the mod asks with the engine's question card (`$.ui.ask`) instead of a pane, and records the choice, within the `classic.Elicitation` hook: the hook returns `{ block }` once the choice is recorded (waiting on `$` does not spend the hook's budget). The choice is not recorded from a `$.clock.after` timer: a call the mod's own code makes outside its hooks is not seen by its own `tool.check` hook, so the session's permission rules decide `approval_choice` there. With engine 2.1.299 in the Claude app, in auto mode, the classifier refused it, so the choice never reached the relay and the `js` call waited until Claude Code's idle timeout (2026-10-20). The app marks a session as needing input (its sidebar flag and notification) only for a permission request, which the question card is and a mod pane, toast or `$.ui.notify` is not. The app draws that card itself: only the question text and the option labels show (no header chip, option descriptions, previews or icon; a `ui.render` hook on `AskUserQuestion` is ignored there, and `$.ui.ask` bypasses `tool.call` hooks). So the question carries the app and its bundle id, "Computer use will be able to see and control Zed (dev.zed.Zed). Allow it?", and for a `high` risk starts with "⚠️ High risk —" and puts the runtime's warning before "Allow it?". The options are those of the pane. Closing or skipping the card resolves the question with the engine's "[User dismissed ...]" note; the mod records that as `cancel`, as Esc on the pane. After the choice is recorded the same confirmation toast shows. A session that reports no surfaces but places panes keeps the pane.

The pane only seats where the surface places it. An unasked pane needs 144 terminal columns; below that `$.ui.open` returns `isPlaced: false`, and the mod asks the same question with the engine's own question dialog, within the hook as in the app (`$.ui.ask`: Allow this conversation, Always allow only if offered, Deny, with the same question text as the app's card). It never leaves the terminal without a prompt. In a headless run (`claude -p`, no attached surface) the hook leaves the event to the host, which answers `cancel` at once as before. If the relay or the mod cannot be reached, the hook falls back to the host's form as well.

The approval cannot be made by the model:

- `approval_choice` and `approval_request` act only for calls whose `_meta["claudecode/toolUseId"]` starts with `toolu_plugin_`, which Claude Code gives to calls a mod makes (the model's ids come from the API). Any other call is refused.
- A choice is bound to its pending id, accepted once, and only for a request the mod has described. It is valid for 30 s after it is recorded. `always` is refused unless the runtime offered it.
- The mod's own `tool.call` hook denies the model's calls to these tools and a `tool.check` hook lets only the mod's calls through without a permission card. Those hooks see only calls made within one of the mod's hook dispatches (`classic.Elicitation`, `ui.press`, `ui.close`), so the mod records every choice from one. (Without the mod Claude Code asks for permission, and the relay refuses the call anyway.)
- These tools cannot be hidden with the deny rules that hide `set_turn_context`: a denied MCP tool is removed from Claude Code's tool list, and the mod's `$.mcp.call` fails with "no tool". They are listed, with descriptions that mark them internal. Deny rules in managed settings do not override a mod; for the same reason do not add these tools to `permissions.deny`.
- A `$.ui.ask` dialog is a real `AskUserQuestion` call that another hook could answer. The mod treats an answer faster than 400 ms or an unknown label (text typed under Other) as Deny, and a dismissal as a cancel. The pane has no such programmatic answer path.

The runtime's risk warning is written for its own product ("Allowing ChatGPT to use this app ... monitor ChatGPT ..."). The pane and the question dialog show it as "Allowing computer use to control this app ... monitor the agent while it uses this app", and any other "ChatGPT" as "the agent"; the record the relay keeps is unchanged. The app's icon is drawn only on a terminal that draws pictures (kitty, Ghostty; detected from `TERM_PROGRAM`, `KITTY_WINDOW_ID`, `GHOSTTY_RESOURCES_DIR`, `TERM`, not under tmux), so other terminals start the name at the pane's edge.

**Approved apps panel.** The mod registers the slash command `/computer-use-apps` (`session.start`), which opens an "Approved apps" pane. It lists the apps in the always-allowed store (`lcu apps --json`) one line each (name, the dim bundle id, a "High risk" or "Blocked" badge, Revoke at the right), with the entries that are no longer installed grouped at the bottom under "Not installed (n)" and still revocable; Refresh sits beside the subtitle so it never meets the pane's close mark, and a list taller than the pane (capped at 26 rows) scrolls with the engine's own pane scrolling. It also shows this conversation's grants read from `~/.codex/computer-use/sessions/<Claude session id>.toml` (`[apps] allowed`; `$CODEX_HOME` is honored), marked "Ends with this conversation". Conversation grants have no Revoke: the runtime owns and rewrites that file, and editing it from outside is not known to be safe. High risk is known for always entries (from `lcu apps`) and for conversation grants made through the pane; other conversation grants show no marker. Revoke runs `lcu apps revoke <bundle id>` and the "Allow an app" field runs `lcu apps allow <name>`; the command itself shows the macOS Touch ID or password prompt, the pane shows "Confirm with Touch ID or your password..." meanwhile, then the command's message (or its error) as a toast and a line in the pane, and the list is read again. The `lcu` executable comes from `lcu.json` beside the mod, which `lcu setup` writes (`<prefix>/current/bin/lcu`), else `~/.local/share/lcu/current/bin/lcu`; if neither exists the pane says to rerun `lcu setup --agent claude-code`. Every side effect (running `lcu`, `sips`, reading files) is in an event hook (`command.run`, `ui.press`, `ui.input`, `classic.Elicitation`), never in a render closure.

The mod is the trusted code of the person's own machine: it can approve anything the person could. It sits in a skills folder (`~/.claude/skills/lcu-approve`, or `<project>/.claude/skills/lcu-approve` for project scope), which Claude Code loads without the hot-reload question (an organization allowlist that does not include `skills-dir` plugins disables it). Mods are on by default in Claude Code 2.1.287 and later; the 2.1.286 build bundled with the Claude app already contains them.

The Claude tools fall into three groups. Model tools (`js`, `js_reset`) are the only ones `--approval auto` allows. Host-only tools (`set_turn_context`, `turn_ended`, `js_add_node_module_dir`) stay in `permissions.deny`. The mod-only approval tools (`approval_request`, `approval_choice`) are neither allowed nor denied, because a denied MCP tool leaves the tool list and the mod could not call it; the relay refuses them unless the tool-use id starts with `toolu_plugin_`. The host-app guard below runs first in the elicitation handler, so a refused host app is declined before any pending approval exists and the mod never shows a pane for it. `tests/node/approval.test.mjs` checks that the model tools in `lcu/approval.mjs` match `MODEL_TOOLS` in `adapters/client.mjs` and `PUBLIC_TOOLS` in `adapters/claude.mjs`, and that the mod-only tools match `MOD_ONLY_TOOLS` in the relay.

Verification: `adapters/test/claude.test.mjs` and `adapters/test/approval-broker.test.mjs` cover the relay and the choice rules; `claude plugin test adapters/claude-mod/lcu-approve` runs the mod against the engine's test kit; `python3 tests/claude_approval_mod.py --claude PATH` drives a real interactive Claude Code (with a scripted local Messages API and the relay in front of the original-runtime fixture, a temporary HOME, no model and no computer use) through the pane, the narrow-terminal dialog, dismissal, a slow answer (past the hook's 10 s) and the model's refused calls. Its `desktop-session` and `desktop-slow` scenarios run Claude Code as the Claude app does (stream-json, permission requests sent to the host, a `ui_attach` of the desktop surface), answer the question card the way the app does (after 3 s and after 75 s), and fail if any other permission request reaches the host; they run without the `mcp__lcu` allow rule the terminal scenarios add, as `lcu setup` adds none. It needs a Claude Code with mods; the `claude` of 2.1.204 has none. The Claude app itself has not been driven by this record; the app's question-card path is covered by the test kit and the desktop scenarios above (with engine 2.1.299) only (that a `$.ui.ask` card flags the session in the app was observed with engine 2.1.295 on 2026-10-14, before the mod used it).

### Claude turn identity and cross-turn Computer Use

The original service ends a turn by id: after `turn_ended` for an id, it refuses calls for that id. Claude Code hooks give the relay a session id, a prompt id and, inside a subagent, an agent id; subagents and the turn that started them share the prompt id, and a turn woken by a background task notification gets a new one. The relay binds the identity at `PreToolUse` and sends `turn_ended` on `Stop`, `SubagentStop` and `Interrupt`.

- **Subagents (always).** Each subagent gets its own upstream turn id, a UUID derived by hash from its agent id and prompt id, so its `SubagentStop` ends only itself. Before this, a foreground subagent finishing ended the parent's still-running prompt id and the parent's next call was refused. The derivation needs no stored map, so evicting history can never end a parent's id.
- **Setting off (default).** The original rule: Computer Use ends with the turn. A parent `Stop` or `Interrupt` closes the prompt at once, whatever the original service answers (an unclear reply fails closed and is not rolled back), and cascades `turn_ended` to the prompt's live subagents, as when they shared its id. A subagent that starts after its prompt closed shares the closed id and is refused.
- **Setting on** ([`lcu cross-turn on`](INSTALLATION.md#cross-turn-computer-use)). A parent's `Stop` ends only the parent. A key (main or subagent) that binds again after its upstream turn ended, or while that end is in flight, gets a fresh random upstream id for this life and its later `turn_ended`, so background subagents keep working after the parent's `Stop` and a reused prompt id works. A life that was ended or cascaded while the setting was off is renewed the same way.

The relay keeps one record per life of a turn key (session or agent, prompt id): the upstream id it uses, whether that id is known or assumed ended, and its cleanup in flight, so a cleanup always targets its own life and a re-bind never inherits another life's end. Live turns are capped at 1024 (a new turn is refused, never an existing one). Ended keys and closed prompts are remembered in bounded sets of 65,536 each, evicted oldest first by when they were last recorded (not by use). For an extremely old key or prompt that has been evicted, behavior falls back to the prior one: with the setting off a child of a prompt closed that long ago is no longer refused by the relay, and with it on a re-bind of an evicted main key forwards its prompt id, which the original service may refuse, while an evicted subagent key defaults to its deterministic hash. Shutdown tracks every `turn_ended` still pending, including those of superseded lives, but closes the upstream connection when the shared two-second drain deadline expires, whether or not they have answered.

The relay reads `cross-turn.json` (`adapters/cross-turn.mjs`, shipped in the archive's `adapters`) each time it decides. Per-app approvals are unchanged. Only the Claude relay reads the setting; the other agents ignore it. Codex hooks carry Codex's own turn id and Pi (and Oh My Pi, which wraps it) generates a UUID per turn; both were read in code only. [Record](verification/cross-turn-2026-10-10.md).

### Turn end before js_reset

`js_reset` stops the original trusted worker. That worker holds the turn-ended hook and pending turn data of every turn that ran `js` on it, so a turn end after the reset reaches no hook, and on macOS Sky keeps that turn's event taps. Before forwarding `js_reset`, every relay (Claude, Codex, and the shared client used by Pi, Oh My Pi and Hermes) sends the original `turn_ended` (Interrupt) for each turn that ran `js` on the current worker. That turn's later calls and its own `turn_ended` then carry a fresh random upstream id, which the original service accepts. `turn_end` diagnostic events say whether the end could reach the hook (`sky_hook`: `live`, `reset` or `none`). [Record](verification/sky-event-taps-js-reset-2026-10-10.md).

### Update notices

The `lcu-approve` mod also runs `lcu update --notice --json --announce=<session_id>` when a session starts and on prompts, at most every 10 minutes per session (a cache read; the cache itself refreshes in the background every 10 minutes). `--announce` applies the same rule as the Codex hooks, in the same `announced.json`: a release is announced at most once a day per account, across all Claude Code and Codex sessions, each session is told about a given release once, and a newer release is announced at once. A session not told during the cooldown may be told at its next prompt after it. The toast follows the same decision; the mod keeps no cooldown of its own. When a newer release is cached, the user sees a toast; the hook's result is returned unchanged, so the model never receives the notice. The command reads only the local cache and never blocks the session start; see [update notices](INSTALLATION.md#update-notices). `LCU_NO_UPDATE_CHECK=1` disables it.

The Pi and Oh My Pi extension (`adapters/pi/index.ts`) runs the same command, with Pi's session id, on `session_start` when `ctx.hasUI` is true, through the release launcher its MCP command starts (3 s timeout; any failure means no notice), and shows the message with `ctx.ui.notify` (a warning for security and breaking releases, else info). It returns nothing to Pi, so the model never receives the notice. `adapters/test/pi.test.mjs` covers it with a fake launcher; it has not yet been observed in a live Pi or Oh My Pi session. Hermes, DeepSeek Harness and Junie have no equivalent yet; their notice appears in `lcu status`, `lcu doctor` and `lcu update --check`.

## Harnesses installed after setup

Registration stays with each harness's own tool: `pi install`, `omp plugin link`, `hermes plugins enable`, `dsh plugin add`, and the pinned add-mcp for Codex and Claude Code. LCU adds no configuration writer for them. Pi, OMP, Hermes and DeepSeek Harness cannot be registered without their executable, so `lcu setup --allow-missing` records an absent one as pending in `setup.json`, and `lcu setup --reconcile` later runs the same registration step once the executable exists, with the saved Chrome, audio and approval mode. Codex, Claude Code and Junie write plain user configuration and register immediately. The user-facing behavior is in [Harnesses installed later](INSTALLATION.md#harnesses-installed-later). Reconcile only calls the existing registration code; a pre-written Pi extension, OMP link or Hermes plugin entry is deliberately not used because those registries belong to the harness.

## Approval boundary

An approval lasts as long as the person needs; no LCU or SDK timer ends it. The Claude and Codex relays forward each request downstream without the MCP SDK's default 60 s request timeout, and the shared client waits on `onElicitation` the same way. While any approval is pending, the deadline of every tool call (`TURN_END_TIMEOUT_MS`, or a `js` call's requested run plus 30 s) stands still and resumes with its remaining time afterwards, so a call that is genuinely hung still expires. Aborting the tool call (interrupt or turn end) cancels the pending approval at once: the relays pass the abort signal downstream, and the shared client resolves `onElicitation` as cancelled and passes `{ signal }` to it (Pi forwards it to its selector). Hermes shows the selector synchronously and does not cancel it on abort. The host's own limits on how long it keeps a prompt or a tool call open are outside LCU.

Native-app approval requests come from the original runtime only on macOS and Windows. The original Linux runtime (observed in ChatGPT 26.915.31945 and 26.930.41038) has no per-app approval: an MCP client that supports elicitation receives no request while `js` lists, focuses and types into any window. On Linux, harness approval of LCU's tools is therefore the only gate before desktop control.

The supported native-app and external Chrome flows have not produced generic schema-field or URL-mode approval requests. Those unobserved shapes are not baseline parity failures. Current tests preserve the original message, origin, and requested native-app persistence scope; a host that cannot present a request fails closed.

Harness approval of LCU's own tools is separate from those requests and is the harness's decision by default. Per-app approval holds in every harness permission mode, including `--approval auto`, which is optional and meant for unattended machines. The optional [approval mode](INSTALLATION.md#approval-mode) (`lcu setup --approval auto|ask`) adds or removes only LCU's entries, reversibly. Every entry names the model-visible tools `js` and `js_reset` exactly, never the whole `lcu` server, so a tool LCU adds later (including one annotated as requiring the user) is not allowed by an earlier `auto`; host-only tools are never allowed:

| Harness | Default | `auto` entry |
| --- | --- | --- |
| Claude Code | asks before each tool call | `permissions.allow: ["mcp__lcu__js", "mcp__lcu__js_reset"]`; host-only tools stay in `permissions.deny` |
| Codex CLI | asks before each call (`codex exec` cannot run it under approval policy `never`) | `approval_mode = "approve"` under `[mcp_servers.lcu.tools.js]` and `[mcp_servers.lcu.tools.js_reset]` (Codex resolves a tool's `approval_mode` before the server-wide `default_tools_approval_mode`, which LCU no longer writes) |
| Oh My Pi | no prompt in the default `yolo` mode | `tools.approval.js` and `.js_reset` set to `allow`, for profiles in `always-ask` or `write` mode |
| Pi | no permission system | none |
| Hermes | no gate on plugin tools without a `pre_tool_call` hook, which LCU does not register | none |
| DeepSeek Harness | no gate on plugin tools without a `tools/pre-execute` listener, which LCU does not register and DSH's base bundle does not ship | none |
| Junie | the interactive TUI asks before each MCP call | `{"pattern": "lcu:js", "action": "allow"}` and the same for `lcu:js_reset` in `rules.mcpTools.rules` of `~/.junie/allowlist.json` |

Manual checks outside the repository fixtures found that Claude Code 2.1.204 auto-approves `mcp__lcu__js` with the server-wide `mcp__lcu` rule that earlier versions wrote (the exact rule has the same effect for the tool), and that Codex CLI 0.159.3 prompts `Allow the lcu MCP server to run tool "js"?` by default, runs the tool without prompting with the setting, and prompts again once it is removed. `tests/codex_approval_mode.py` reproduces the Codex difference with a scripted provider and an isolated home; with the per-tool entries it passed on Codex CLI 0.160.0; the Claude Code and OMP entries are covered by unit tests and no scripted Claude Code or model-driven OMP run is recorded. OMP's key names come from its `tools.approval` setting, which the policy resolver reads by tool name. `tests/node/approval.test.mjs` asserts that the Claude Code allow rules are exactly the model-visible tools, that no host-only tool or wildcard appears in them, and that LCU's (`lcu/approval.mjs`), the Claude relay's and the shared client's lists of model tools agree. Entries changed by the mode never include native-app or Chrome approvals, so Chrome site approvals remain exact-origin only.

### Agent host apps are never approved

Computer use can click buttons in any approved app, so approving the app that shows this agent's own approval prompt would let the agent approve itself. `adapters/host-guard.mjs` answers `decline` to a native-app approval request (`_meta.connector_id` `computer-use` with `tool_params.app`) without asking the host or user for: (a) every app bundle that is an ancestor of the adapter process (found with `ps` and each bundle's `CFBundleIdentifier`; the official app's own Node bundle is skipped), so Claude desktop, an editor running the Claude or Codex extension, or the terminal running a CLI agent is covered whatever it is; and (b) a static list of dedicated agent hosts and terminals: Claude desktop (`com.anthropic.claudefordesktop`), the Claude Code CLI bundle (`com.anthropic.claude-code`), Codex, OpenCode, Factory, Hermes, DeepSeek Harness (`com.deepseek.dsh`), Terminal, iTerm2, Ghostty, Warp, WezTerm, Alacritty, kitty, Hyper, Rio and Wave. Editors and IDEs (VS Code, Cursor, Windsurf, Antigravity, Zed, Xcode, JetBrains) are deliberately not listed because they are common computer-use targets; when an agent extension hosts the session the editor is an ancestor of the adapter and detection (a) refuses it. The runtime already forbids Terminal, iTerm2 and `com.openai.codex`; the overlap is harmless. The guard runs in the Claude relay, the Codex relay and the shared client (Pi, OMP, Hermes, DeepSeek Harness), before any original-runtime reply is relayed. A failed or unavailable process lookup falls back to the static list. The Claude Code and Codex relays log `LCU does not allow computer use to control the app hosting this agent (<name>)` to their stderr; the shared client (Pi, Oh My Pi, Hermes) writes nothing to the harness terminal and the diagnostic log records the refusal as approval kind `agent_host_refused`; the model sees the runtime's own "Computer Use was not approved to use <app>" error, because an elicitation reply cannot carry text. Set `LCU_ALLOW_AGENT_HOST_APPROVAL=1` in the adapter's environment to disable the guard, for testing the approval flow only. Detection runs on macOS; Linux has no per-app approval and Windows app ids are not in the list.

The [contract audit](verification/harness-contract-audit-2026-09-25.md) records the primary-source review and scope boundaries. Full platform installation steps are in the [installation guide](INSTALLATION.md).

## Diagnostic log

The Claude Code and Codex relays and the shared client (Pi, Oh My Pi, Hermes) keep a local diagnostic log so a call that hangs can be explained afterwards: per call it shows when the call started, whether an approval was opened for it and for which app, whether the `lcu-approve` mod claimed that approval, what choice came back, and how the call ended. The log is written by `adapters/diagnostics.mjs`. It never throws and never changes a call's result: any filesystem error turns the log off for that process.

**Location.** One file per adapter process, `<adapter>-<UTC YYYYMMDDTHHMMSSZ>-<pid>.jsonl` (adapter `claude`, `codex`, `pi`, `omp`, `hermes`, `dsh`, `junie` or `client`), one JSON object per line (`{"t":"<ISO UTC ms>","event":"...",...}`):

| Platform | Directory |
| --- | --- |
| macOS | `~/Library/Logs/LCU/` |
| Linux and others | `${XDG_STATE_HOME:-~/.local/state}/lcu/logs/` |

`LCU_LOG_DIR` overrides the directory. The directory is created with mode `0700` and files with `0600`. `lcu status --json` (`diagnostic_log`) and `lcu doctor` print the directory and policy.

**Recorded.** Metadata only: the adapter name, LCU version, platform, architecture and pid; the tool name, the requested `timeout_ms`, durations in milliseconds and outcome (`ok`, `tool_error`, `timeout`, `aborted`, `error`) with a numeric MCP error code when there is one; a per-process call number that ties events together; the approval kind (`native_app`, `browser_origin`, `agent_host_refused`, `other`), the approved app's identifier (the bundle id or name the runtime puts in `_meta.tool_params.app`, so the log does name the apps you were asked to approve), the persistence scopes offered, the choice (`session`, `always`, `deny`, `cancel`) and the approval's final action; turn-end events and their outcome (`hook_event` `Stop`, `Interrupt` or `SubagentStop`); in the shared client, one `upstream_stderr` event per stderr line of the original MCP process; and, in Pi, one `surface_changed` event (`tools_changed`, `instructions_changed`) when a connect reports tools or instructions that differ from the cached surface.

**Original process stderr.** The shared client records each line the original MCP process writes to stderr (including LCU's macOS host and service) as `{"event":"upstream_stderr","kind":"..."}` and never its text. `kind` comes from the line's known prefix: `turn_ended_slow` (the signed `turn-ended` command exited 0 but took at least 4.5 s), `turn_ended_failed` (it exited non-zero, timed out, could not start, or failed in the service's retry), `cleanup_step_slow` (a turn cleanup step took at least 1 s or is still running at the hook's deadline), `turn_cleanup_failed`, `user_control_unavailable`, `control_request_failed`, `stale_service_recovery`, `sandbox_refused`, `sandbox_note` or `other`. Only numbers and flags parsed from a known line are added: `exit_code`, `timed_out`, `launch_failed`, `elapsed_ms`, `has_stderr` (the command wrote stderr; its text is not kept), `retry`, `still_running` and `exited`. A process records at most 500 such events; the 500th is followed by one `upstream_stderr_limit` event, and later lines are read and counted but not recorded, with one `upstream_stderr_dropped` event (`lines`) when the stream ends. The Claude Code and Codex relays leave this stderr to their harness and record no such events.

**Never recorded.** Tool arguments (the JavaScript the model ran), tool results (text or images), approval messages, window, UI or accessibility text, error message text, the text of the original process's stderr, file contents, or raw session, turn or tool-use ids.

**Retention.** When an adapter process opens its log, before it creates its file, it deletes log files in that directory (only names matching the pattern above) whose modification time is older than 7 days, then deletes the oldest of the remaining ones until they total at most 20 MiB. A single process stops writing when its file reaches 2 MiB: it writes one final `{"event":"log_full"}` line and drops later events. The constants are exported from `adapters/diagnostics.mjs` and mirrored in `lcu/diagnostic_log.mjs`, and `tests/node/diagnostic_log.test.mjs` keeps them equal.

**Control.** `LCU_DIAGNOSTIC_LOG=0` in the adapter's environment turns the log off completely: no directory, no file and no pruning. To delete the logs, remove the directory. The files stay on this computer; LCU never uploads them. Review a log before sharing it, since app identifiers and timing are recorded.

Verification: `adapters/test/diagnostics.test.mjs` covers location, retention, the size cap, permissions and failure; `adapters/test/claude.test.mjs` checks that a relayed call and approval are logged and that code, results and approval messages are not. `adapters/test/upstream-stderr.test.mjs` runs the shared client in a child process against a fixture that writes the known stderr lines: the child's stderr stays empty, the log holds the classified events and none of the text, `LCU_DIAGNOSTIC_LOG=0` writes nothing, and 4 MB of stderr is drained without blocking and logged within the event limit. `tests/test_hermes_harness.py` checks that the Hermes plugin process writes nothing to stderr while the bridge floods its own.
